# 编程流程（计划-执行-自查）

打包内置插件，编程任务的标准流程：**先计划 → 按计划执行 → 自查交付**。

## 工具

- **coding_plan**：生成结构化任务计划框架（编号任务树/动词开头/边界/状态标记/验证段/紧凑）。编程任务动手前调用，填充具体内容后按序执行。
- **coding_review**：交付前代码审查清单（安全/完整性/回归/一致性/文档五类自查点），逐项勾选给证据。

## 流程

1. 接到编程任务 → `coding_plan(task=...)` 出计划（编号任务树 + 边界 + 验证段）
2. 按计划执行：分析 → 实现 → 验证（每步用宿主自带工具：Read/Grep/Write/Edit/Typecheck/Test）
3. 执行中计划有误 → 显式更新计划再继续（状态标记 [待办]/[进行中]/[完成]）
4. 交付前 → `coding_review(scope=...)` 自查（安全/完整/回归/一致/文档）
5. 全部通过才交付汇报

## 纪律

- 思考后台化，输出只给计划/结论（紧凑、不废话）
- 改完自证没改坏：typecheck + 测试 + 行为断言；UI 改动用 ui_snapshot baseline/verify
- 大文件不整读烧 token：流式/抽样/搜索定位
- 修到能用为止，减少实测轮次

## 注释规范（硬性）

- 写注释必须说清三件事：这段代码为什么存在、什么作用、需要留存的理由；三者缺一不可。
- 全面检查后判定无需留存的代码/注释：直接删除，不留占位；需要时从版本历史找回。
- 不写自明注释（`// 加 1` 这类），注释解释意图与取舍而非抄代码。
