# 安全专项审查 Security Review

> **领域级技能 · 接入说明**：本技能属于「安全」领域大类（domain: `security`）。安装后存放于 `skills_domains/security/`，运行期不注入技能清单——系统只注入领域名与技能数量，AI 自行用 Grep/Glob 检索 `skills_domains/security/` 目录定位 SKILL.md（frontmatter 的 name/description 判断是否匹配），再用 `use_skill(skill_name=security-review)` 加载本技能正文后执行。

## 为什么存在

通用代码审查会看安全和性能，但安全审查的深度不同：它不是"顺带看一眼"，而是站在攻击者视角系统排查——哪里有输入、到哪里结束、谁能触达、能造成什么损失。本技能把专业安全团队的经验固化成可执行的流程与清单：威胁建模、漏洞模式、语言/框架专项检查、依赖与配置核查，覆盖从发现到修复建议的完整闭环。

## 什么时候用

- 上线前的安全专项审查（不替代通用 `code-review`，在它之后做）
- 涉及认证、支付、用户敏感数据的模块改动
- 新增外部依赖、网络接口、文件上传、命令行执行等攻击面
- 安全事件复盘后，对相关代码路径做全链路排查
- 定期对存量代码做威胁建模与风险盘点

## 审查流程

分五步走完，每一步输出都进入最终报告。

### 第一步 · 威胁建模（先想攻击面）

1. 列出系统的资产：用户数据、密钥、支付、文件、对外接口
2. 列出入口点：所有接收外部输入的位置（请求参数、表单、上传、WebSocket 消息、配置文件、环境变量来源）
3. 对每个入口回答：谁可以触达？不经过验证能否触达？触达后影响什么？
4. 产出威胁清单，按"可触达 × 影响"排优先级

### 第二步 · 按语言/框架查漏洞模式

按项目实际使用的技术栈执行对应清单（每项标 ✅ 通过 / ⚠️ 存疑 / ❌ 问题）：

**Web/JS/TS 通用**
- [ ] SQL/查询注入：所有外部输入走参数化或 ORM，禁止字符串拼接
- [ ] XSS：用户内容渲染前转义；危险 HTML 插入有理由且已验证；CSP 已配置
- [ ] CSRF：状态变更请求带 CSRF 令牌或 SameSite 已设置
- [ ] 开放重定向：跳转目标做了白名单校验
- [ ] SSRF：服务端请求外部 URL 时校验协议与目标，禁止直接透传用户输入
- [ ] 不安全反序列化：不反序列化不可信数据；`JSON.parse` 不执行代码

**认证与访问控制**
- [ ] 每个受保护端点先鉴权再处理，无 IDOR（水平越权）与权限缺失（垂直越权）
- [ ] 会话令牌：随机、过期、不在 URL 中传递；Cookie 加 HttpOnly/Secure
- [ ] 密码/密钥：不硬编码、不落日志；密码哈希用安全算法（如 bcrypt/argon2）
- [ ] 速率限制：登录、验证码、公开接口有防爆破措施

**Node/Electron 专项**
- [ ] `nodeIntegration` 关闭或最小化；外部内容不进 `eval`/`Function` 构造器
- [ ] 加载远程内容时设置严格 CSP，禁用危险协议与内联执行
- [ ] 文件路径拼接经过规范化，防目录穿越；上传文件校验类型与大小
- [ ] 依赖树检查：新增依赖来自可信源、无已知 CVE、维护活跃

### 第三步 · 敏感数据与日志核查

- [ ] 密钥、令牌、个人数据不进入日志、错误消息与响应体
- [ ] 数据库字段级权限与脱敏策略存在（身份证、手机号等）
- [ ] 传输加密：TLS 用于所有对外通信
- [ ] 机密不写入源码与配置文件；通过环境注入或密钥管理服务读取

### 第四步 · 验证漏洞（不只看代码）

- 对每项 ❌ 问题，说明：入口在哪里、攻击者如何构造输入、影响面多大
- 有条件时做最小验证（本地起服务、构造请求），不能只凭猜测断言可利用
- 明确哪些结论是已验证事实、哪些是待验证推断

### 第五步 · 输出报告

按下方模板输出，问题按严重级别排序。

## 输出模板

```markdown
## 安全审查报告

### 审查范围
- 代码范围：____
- 技术栈：____
- 威胁建模入口清单：____

### 高危问题（必须修复后才能上线）
| # | 位置 | 问题 | 攻击路径 | 修复建议 | 验证方法 |
|---|------|------|---------|---------|----------|

### 中危问题（建议尽快修复）
| # | 位置 | 问题 | 修复建议 |
|---|------|------|----------|

### 低危/加固项
- ____

### 已确认安全项
- ____

### 结论
- [ ] 高风险项全部关闭 / 有明确修复计划与责任人
```

## 严重级别

| 级别 | 含义 | 上线门槛 |
|------|------|---------|
| 高危 | 可被外部直接利用，造成数据泄露、越权、服务不可用 | 必须修复 |
| 中危 | 需特定条件才能利用，或影响面受限 | 尽快修复 |
| 低危 | 加固项、纵深防御建议 | 规划处理 |

## Gotchas

- **不要只报问题不给路径**：每条高危必须写清"攻击者怎么进来"，否则负责修复的人无法复现
- **区分事实与推断**：能验证的写验证结果，验证不了明确标注"待验证"，禁止把推断写成漏洞事实
- **看全链路而非单点**：漏洞往往在"输入→处理→输出"的中间环节，只盯入口或只盯出口都会漏
- **安全审查不等于扫描工具**：工具结果当线索，误报与漏报都要人工核对
- **不要无限扩大范围**：按第一步建模的入口清单审查，临时发现的越界风险单独记录，不无限蔓延

## 完成标准

- [ ] 威胁建模完成，入口清单与资产清单齐全
- [ ] 语言/框架专项清单逐项核对，标注 ✅/⚠️/❌
- [ ] 每条高危问题都有攻击路径、修复建议与验证方法
- [ ] 已验证项与待验证项明确区分
- [ ] 报告按模板输出，结论给出上线门槛判断
