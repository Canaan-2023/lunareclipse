# 代码库侦察 Codebase Recon

> **领域级技能 · 接入说明**：本技能属于「代码」领域大类（domain: `code`）。安装后存放于 `skills_domains/code/`，运行期不注入技能清单——系统只注入领域名与技能数量，AI 自行用 Grep/Glob 检索 `skills_domains/code/` 目录定位 SKILL.md（frontmatter 的 name/description 判断是否匹配），再用 `use_skill(skill_name=codebase-recon)` 加载本技能正文后执行。

## 为什么存在

接手一个新代码库时最常问的三个问题：哪里最常改？哪里最容易出 bug？哪些地方只有一个人懂？这三个答案决定先看哪里、改哪里、风险集中在哪里。本技能用 Git 历史回答这三个问题——提交记录是可审计的行为数据，比人肉阅读更客观，能直接支撑行动决策。

## 什么时候用

- 接手不熟悉的新项目，需要快速建立「哪里能碰、哪里不能碰」的认知地图
- 评估既有代码库的健康度，为重构或技术债治理排优先级
- 定位改动最频繁、最容易出问题的高风险区域
- 识别知识孤岛——只有一个人改过的关键文件（巴士因子风险）
- 代码审查前先侦察改动热区，把审查精力投到高风险文件上

不用于：理解单个功能的具体实现（用 `codebase-inspection`）、审查单次改动（用 `code-review`）。

## 侦察流程

按顺序完成四步，每一步都有明确的输入与输出：

### 第一步 · 校准分析窗口并收集 Git 历史

**先按仓库规模校准窗口**（窗口太窄统计失真，太宽噪音淹没信号）：

| 仓库规模 | 判定（提交数） | 分析窗口 WINDOW |
|---------|--------------|----------------|
| 小型 | < 500 | 全部历史（不设窗口） |
| 中型 | 500–5000 | 最近 1000 次提交 或 最近 6 个月 |
| 大型 | > 5000 | 最近 2000 次提交 或 最近 12 个月 |

用 `git log` 取提交记录，需要提取：每次提交的哈希、日期、作者、改动文件列表；以及提交信息中标记 bug 修复的关键字（`fix`、`bug`、`hotfix`、`patch`）。

### 第二步 · 计算七项指标

对收集到的历史逐文件聚合，得出指标（前四项为核心，后三项为补充判断）：

1. **热点文件（Hotspot）**：提交中改动次数最多的文件。改动频繁 = 需求频繁变化或架构不稳定，是重写与冲突的温床。
2. **Bug 磁铁（Bug Magnet）**：bug 修复类提交中反复出现的文件。修过多次仍未稳定 = 存在显式或隐式的设计缺陷。
3. **巴士因子（Bus Factor）**：仅由一个作者改动过的文件。只有一个人懂 = 此人缺席时无人能安全维护。**定量警示：活跃贡献者占比 < 30% 时单作者文件风险显著上升。**
4. **高风险文件（High-Risk）**：热点与 Bug 磁铁的交集，出现即优先处理。
5. **团队势头（Team Momentum）**：近期各文件的提交频率是否上升/下降。势头上升的热点文件往往预示需求扩张期的新缺陷温床。
6. **救火频率（Firefighting）**：同一文件被紧急修复（`hotfix`/`emergency`/紧密提交对）的频率。反复救火 = 设计缺陷 + 流程问题。
7. **活跃贡献者占比（Active vs Total）**：窗口内活跃作者数 / 历史总作者数。占比低 = 知识正在流失，单点依赖风险高。

### 第三步 · 交叉定位高风险区

- 高风险文件 = 高频改动 + 高频修 bug，最优先关注
- 孤岛文件 = 热点中的单作者文件，需要扩散知识
- 活跃作者占比 < 30% 的仓库，优先排查关键路径上的单作者文件
- 同时命中的文件用严重级别标记，给出核实顺序

### 第四步 · 输出侦察报告

按下方模板输出，结论按风险从高到低排列。

## 输出模板

```markdown
## 代码库侦察报告

### 全景概览
- 分析窗口：____（日期范围 / 提交数）
- 涉及文件总数：____
- 活跃作者数：____

### 高风险文件（热点 ∩ Bug 磁铁）
| 文件 | 改动次数 | 修 bug 次数 | 主要作者 | 建议动作 |
|------|---------|-----------|---------|----------|

### 热点文件（前 N）
| 文件 | 改动次数 | 最近改动日期 | 主要作者 |
|------|---------|------------|----------|

### Bug 磁铁（前 N）
| 文件 | 修 bug 次数 | 常见症状 | 建议 |
|------|-----------|---------|------|

### 知识孤岛（单作者文件）
| 文件 | 作者 | 最后改动 | 风险 |
|------|------|---------|------|

### 行动建议（按优先级）
1. ___
```

## Gotchas

- **提交频率不等于业务重要性**：自动生成的代码、打包产物可能改动频繁但无业务价值，先排除这类文件（如 `dist`、锁文件）
- **小仓库无统计意义**：提交少于 50 条的仓库指标波动大，结论降级为参考而非结论
- **改名或迁移文件会失真**：文件路径变更后历史被切断，优先用 `git log --follow` 跟踪重命名
- **不要只看数字**：指标用于定位，结论必须配合读代码核实，禁止仅凭统计下判断
- **团队协作特性**：结对编程、集体提交会稀释单作者判断，巴士因子要结合代码评审记录确认

## 完成标准

- [ ] 已按仓库规模校准分析窗口（小型全量 / 中型 1000 提交 / 大型 2000 提交）
- [ ] 七项指标（热点/Bug 磁铁/巴士因子/高风险/团队势头/救火频率/活跃贡献者占比）逐文件计算完成
- [ ] 排除了自动生成与打包类噪音文件
- [ ] 高风险区域已交叉核实，结论附具体文件与证据
- [ ] 活跃作者占比 < 30% 时已评估单点依赖风险
- [ ] 输出按模板生成，行动建议按优先级排序
