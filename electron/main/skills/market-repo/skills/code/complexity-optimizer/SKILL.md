# 代码复杂度优化 Complexity Optimizer

> **领域级技能 · 接入说明**：本技能属于「代码」领域大类（domain: `code`）。安装后存放于 `skills_domains/code/`，运行期不注入技能清单——系统只注入领域名与技能数量，AI 自行用 Grep/Glob 检索 `skills_domains/code/` 目录定位 SKILL.md（frontmatter 的 name/description 判断是否匹配），再用 `use_skill(skill_name=complexity-optimizer)` 加载本技能正文后执行。

## 为什么存在

代码库膨胀后最大的隐性成本不是行数，而是复杂度：分支多、嵌套深、职责混的函数最难理解、最难测试、最容易藏 bug。泛泛的"建议优化"没有价值，本技能用可量化的复杂度指标（圈复杂度、认知复杂度）定位过剩复杂度，输出"拆成几个、每个多简单"的具体方案，让重构有目标、有验收标准。

## 什么时候用

- 代码库逐渐膨胀，需要对项目做定期"代码体检"
- 定位"写的时候好好的、一改就炸"的函数与模块
- 为重构排定优先级——先拆最复杂的，收益最大
- 审查或合并前，确认改动没有引入复杂度爆炸
- 用指标说服团队：某个模块确实需要治理，而不是凭感觉

不用于：审查单次改动的逻辑与安全（用 `code-review`）、理解项目结构与定位功能（用 `codebase-inspection`）。

## 优化流程

按顺序完成四步，指标只用于定位，方案必须落到可执行的重构动作。

### 第一步 · 度量复杂度

对目标文件/模块逐函数计算两个指标：

| 指标 | 计算方式 | 阈值（超标标记） |
|------|---------|----------------|
| 圈复杂度 | 独立路径数 = 判定点 + 1（`if`、`for`、`while`、`case`、`&&`、`||`、捕获分支各计 1） | > 10 需要关注，> 20 必须处理 |
| 认知复杂度 | 判定嵌套加权重：每层嵌套的判定数累乘 | > 15 需要关注，> 25 必须处理 |

可用现成工具辅助统计（如 `eslint complexity` 规则、`lizard`），没有工具时按上表手算圈复杂度。

### 第二步 · 排序与定级

把所有超标函数按严重程度排序，分三级：

1. **P0 · 立即处理**：圈复杂度 > 20 或认知复杂度 > 25，且处于核心业务路径
2. **P1 · 本周处理**：圈复杂度 > 15，或频繁改动仍反复出 bug 的函数
3. **P2 · 规划处理**：复杂度超标但稳定、低频触达的函数

### 第三步 · 生成拆解方案

对每个 P0/P1 函数给出具体重构方案，遵循三条：

- **按职责拆分**：先列出函数在做的所有事，按"一件事一个函数"拆成子函数，每个圈复杂度控制在 5 以下
- **用早退与卫语句压平嵌套**：深层 `if` 嵌套改为条件不满足即返回，减少认知复杂度
- **抽取数据与策略**：大 `switch`/`case` 分支多的，按策略模式映射表替换；重复的条件组合抽取为命名清晰的布尔函数

### 第四步 · 验证与验收

- 拆解后重新度量，确认每个函数达标（圈复杂度 ≤ 5）
- 行为不变性验证：重构前后输入输出一致，现有测试全绿
- 补测试：拆分后的每个子函数至少有一个单测
- **行为证明优先于重构**：没有回归测试保护的函数，优先花时间补测试基线（证明行为不变的能力），而不是直接拆解——拆完无法证明没改坏，重构就不是优化而是赌博

### 优化安全清单（拆解时逐项核对）

重构是结构变换，任何行为漂移都是事故。拆解时按清单确认语义未变：

- [ ] **排序顺序保持**：重复数据、同值不同对象、稳定排序场景下，输出顺序与重构前一致
- [ ] **对象身份与可变性保持**：调用方依赖的引用身份（`===`）、可变对象共享方式不变
- [ ] **缓存与去重语义不塌缩**：合并重复逻辑时，不把"语义不同但长得像"的记录合并；去重不吞掉不同租户/上下文的值
- [ ] **批处理约束保持**：批量操作保持原有的权限、租户隔离、软删除与分页语义
- [ ] **边界行为一致**：空输入、溢出、错误路径、罕见分支的行为与重构前完全一致

## Gotchas

- **复杂度低不等于好代码**：指标只找"过度复杂"，不评估可读性与正确性；配合 `code-review` 用
- **不要为拆而拆**：稳定的、低频改动的函数即使超标也可暂缓，重构也有成本
- **重构不许改行为**：重构是结构变换不是行为变更；发现行为必须改时，把它标成独立缺陷而不是混进重构
- **先有测试再动刀**：没有回归测试保护的函数，先补测试再拆解，否则无法证明行为不变
- **警惕指标游戏**：把函数拆到难以理解的颗粒度来压指标，是拿可读性换数字，违背重构初衷

## 完成标准

- [ ] 目标范围全部函数完成复杂度度量，超标项已定级
- [ ] P0 项全部给出"拆成几个、每个多简单"的具体方案
- [ ] 无测试保护的函数已先补行为基线（或明确说明风险）
- [ ] 优化安全清单逐项核对，重构不改变行为
- [ ] 现有测试全绿
- [ ] 拆解后复测指标，标注还剩哪些未达标的项与原因
- [ ] 报告按模板输出，结论有数字支撑
