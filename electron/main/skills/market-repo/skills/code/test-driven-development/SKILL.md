# 测试驱动开发（TDD）

> **领域级技能 · 接入说明**：本技能属于「代码」领域大类（domain: `code`）。安装后落位 `skills_domains/code/`，运行期不注入技能清单——系统只注入领域名与技能数量，AI 自行用 Grep/Glob 检索 `skills_domains/code/` 目录定位 SKILL.md（frontmatter 的 name/description 判断是否匹配），再用 `use_skill(skill_name=test-driven-development)` 加载本技能正文后执行；正文开头的触发条件就是「何时该加载本技能」的信号。

RED → GREEN → REFACTOR 循环，保证每个功能都有测试兜底。

## 流程

1. **写失败测试（RED）**：为要实现的函数/行为写测试，断言期望结果
   - 测试跑起来必须是失败的（未实现 → 编译错或断言失败都算 RED）
   - 测试粒度：一个行为一个用例，命名说清"什么条件下应该怎样"
2. **最小实现（GREEN）**：写最少的代码让测试通过
   - 不要过度设计，不写测试没覆盖的功能
3. **重构（REFACTOR）**：在测试保护下清理代码（去重复、提函数、改命名）
   - 重构后测试必须仍全绿

## 测试要点

- **测行为不测实现**：断言输入输出的行为，不依赖内部函数名/调用顺序
- **边界用例**：空输入、极端值、错误路径至少各一个
- **测试要快**：纯逻辑测试优先，不要每个用例都起服务/连数据库

## 验证

- 改完跑全量测试：`npm test` / `npm run test:unit`（按项目实际命令）
- 测试全绿才算完成，把测试结果作为交付证据

## Gotchas

- **跳过 RED = 假 TDD**：直接写实现再补测试，测试就失去驱动价值
- **别删测试迁就实现**：测试失败说明实现不对，不是测试不对（除非测试本身写错）
- **重构阶段测试是安全网**：没有测试保护的重构是赌博
- **测试也是交付物**：别人改代码时靠测试知道有没有改坏

## 完成标准

- [ ] 每个行为先写失败测试（RED），再最小实现转绿（GREEN）
- [ ] 重构在测试保护下进行，跑完测试仍全绿
- [ ] 边界用例（空输入、极端值、错误路径）至少各一个
- [ ] 已把测试结果作为交付证据说明
