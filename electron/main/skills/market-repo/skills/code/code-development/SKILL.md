# 代码开发一条龙 Code Development

> **领域级技能 · 接入说明**：本技能属于「代码」领域大类（domain: `code`）。安装后存放于 `skills_domains/code/`，运行期不注入技能清单——系统只注入领域名与技能数量，AI 自行用 Grep/Glob 检索 `skills_domains/code/` 目录定位 SKILL.md（frontmatter 的 name/description 判断是否匹配），再用 `use_skill(skill_name=code-development)` 加载本技能正文后执行；正文开头的触发条件就是「何时该加载本技能」的信号。

## 为什么存在

code 领域的既有技能各管一段：摸库、规划、TDD、调试、简化、复杂度、审查。但真实开发是一次连续旅程——从理解需求到写码再到收尾审查，缺一个统一入口，就容易跳阶段或漏交棒。本技能把这段旅程固定成一条龙：先执行哪个阶段、每阶段按什么标准过、该把工作交棒给哪个既有技能，全部在入口处定好，开发过程不再临时找技能。

## 什么时候用

- 用户要求开发新功能、编写新代码
- 修改、重构、简化现有代码
- 修复 bug、排查异常行为
- 写完一段代码请求自查，或请求审查 PR/diff
- 用户明确要求"按 code-development 流程走一遍"
- 不触发：纯问答、不包含代码的文档写作、纯设计讨论

## 一条龙流程总览

| 阶段 | 动作 | 本阶段完成标准 |
|------|------|----------------|
| 1 理解与规划 | 摸清结构与范围 | 能说清改哪些文件、数据怎么流 |
| 2 开发执行 | 边写码边对照写码纪律 | 每段代码过七条纪律 |
| 3 测试保障 | TDD 优先，遇 bug 走调试 | 相关测试全绿 |
| 4 完成自查 | 提交前快速过一遍检查清单 | 无残留问题 |
| 5 正式审查 | 路由到 code-review 三遍流程 | 输出带严重级别的报告 |

## 阶段一 理解与规划

1. **需求拆解**：这个改动要达成什么行为？写出一句可验收的话。
2. **场景路由**：
   - 不熟悉的代码库、需要定位功能实现 → `use_skill(skill_name=codebase-inspection)`
   - 新接手大项目、要评估质量与高风险区域 → `use_skill(skill_name=codebase-recon)`
   - 改动点已知但影响面不明 → 用 `grep` / `glob` 追调用链，确认谁调用它、它调用谁
3. **输出改动计划**：涉及文件（各一句职责）、数据流、验证方式。

## 阶段二 开发执行 · 写码纪律

每写一段代码先过七条，不满足不往前走（详细定义在 `code-review` 技能的「兜底合规」与「可读性与结构纪律」两节）：

兜底合规三条：

- **不为了兜底而兜底**：没有真实失败场景的兜底不写
- **兜底不改结果口径**：兜底分支与主路径语义一致，状态、返回值、验收标准不变
- **兜底可观测**：触发时返回可感知信号（状态码、日志、提示），不静默吞掉失败

可读性结构四条：

- **命名揭示意图**：函数短到一眼能懂，职责单一，控制流平直
- **不堆屎山**：不堆临时补丁、不留注释掉的死代码，改到哪清到哪
- **拒绝上帝模块**：巨型文件/函数/类按职责拆分，用依赖注入替代全局共享
- **可读性优先于聪明**：不写炫技写法；性能敏感路径必须注释说明原因

阶段内路由：

- 需要可验证性的新功能 / bug 修复 → `use_skill(skill_name=test-driven-development)`（RED→GREEN→REFACTOR）
- 遇到难以定位的 bug → `use_skill(skill_name=systematic-debugging)`（先理解再修复，不盲目试探）
- 简化冗余代码 / 重构去重 → `use_skill(skill_name=simplify-code)`
- 复杂度超标、需要定位于函数级别的重构方案 → `use_skill(skill_name=complexity-optimizer)`

## 阶段三 测试保障

- 项目有测试命令的：改完跑全量测试，把结果作为交付证据
- 新增逻辑必须带对应用例，至少含一个边界或反向用例
- 未覆盖的路径主动说明原因，不假装全绿

## 阶段四 完成自查

提交/交付前快速自查（2 分钟内完成）：

- [ ] **调试残留**：无调试输出残留、无注释掉的死代码
- [ ] **类型与边界**：无 `any` 滥用；空值、边界值已处理
- [ ] **安全底线**：无明文密钥、无未校验的外部输入
- [ ] **兜底合规**：每个 fallback 过一遍三条规则
- [ ] **测试证据**：相关测试全绿或有明确说明

任一命中警告项 → 修完再进下一阶段，不带着已知问题交棒。

## 阶段五 正式审查

- 载入 `use_skill(skill_name=code-review)`，按三遍流程（全貌 → 逐行 → 边界）完整审查
- 输出模板与严重级别定义以 code-review 为准：结论 + `[CRITICAL]/[MAJOR]/[MINOR]/[NIT]` 分级 + 修复建议 + 「做得好」部分
- 审查对象含系统提示词 / 工具描述 / 技能正文 / UI 文案时，追加「面向模型与用户的文本」扫描步骤（黑话、免责句式、歧义句）

## 输出模板

完成一轮开发后按以下结构收尾（审查部分按 code-review 模板细化）：

```markdown
## 改动概览
- 需求：
- 涉及文件：（文件名 + 一句职责）
- 数据流：A → B → C

## 测试证据
- 命令与结果：
- 覆盖说明：

## 审查结论
- （见 code-review 输出模板：结论 + 严重级别分级 + 做得好）
```

## Gotchas

- **别跳阶段**：直接动手写码最常见；至少跑一遍阶段四自查再交付
- **路由优先于硬写**：阶段二先想该不该切 TDD/调试/简化技能，而不是硬写到底
- **纪律是写码时的护栏，不是审查时的补丁**：写完再补七条纪律等于返工
- **自查不等于审查**：阶段四是 2 分钟清单，阶段五必须走三遍并出报告

## 完成标准

- [ ] 需求已拆成一句可验收的行为描述
- [ ] 写码过程对照写码纪律七条自查
- [ ] 相关测试全绿（或已明确说明未覆盖路径）
- [ ] 阶段四自查无残留问题
- [ ] 已路由到 `code-review` 输出带严重级别的审查结论
