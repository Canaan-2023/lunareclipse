# 技能拆分的方法（Split）

本文件是 skill-creator 的「技能太长怎么办」子文档：把一份过大的 SKILL.md 拆成"主体入口 + 子方法文档"，子方法放同技能目录下按需读取。本技能自身就是按此结构组织的实例。

## 什么时候需要拆分

- 正文超过 500 行（lint 上限），或明显"塞不下"
- 一份正文同时承担多件事：入口判断、能力总览、多套方法、字段表、模板
- 经常出现"只需要其中一部分"，但加载正文时全部涌入上下文
- 修订时改动点分散在多处，牵一发动全身

不满足这些条件就不要拆——体积健康的技能拆了反而增加跳转成本。

## 拆分原则

### 1. 主体放什么（SKILL.md）

主体 = 给 AI 的第一眼披露 + 入口 + 路由，只保留四块：

- **frontmatter 披露**：description 写全这个 SKILL 所有能做的事与触发场景（前 60 字符放核心触发词）——这是注入上下文、决定检索的那一份
- **什么时候用**：触发清单（显式触发 + 边界）
- **主体入口判断**：能在这里完成的判断（何时创建、何时沉淀、如何摆放）留在主体
- **子文档路由**：进入执行后需要看哪些方法的清单，指明子文档路径

主体行数目标：50-150 行。超过 200 行说明还有可拆的内容。

### 2. 子文档放什么（同目录）

- 一个方法一个文件：生成方法、融合方法、拆分方法、时机方法论等
- 放到技能目录下的 `methods/`（或 `references/`）子目录，如 `skills/{name}/methods/generate.md`
- 每个子文档还可再细化：子文档太长时拆出二级子文档，仍在该技能目录内
- 子文档的命名用 kebab-case（`generate.md`、`merge.md`、`split.md`），一级路由在主体写明

### 3. AI 怎么按需读取

- 主体路由表写"什么情况 → `Read methods/xxx.md`"，路径为相对技能目录的子文档路径
- 进入对应场景时用 `Read` 读取该子文档，用完全部留在上下文之外
- 需要确认技能目录里有哪些子文档时用 `Glob` 定位
- 与"在技能里放脚本"同理：脚本是何时运行什么，子文档是何时读什么——都是附属资源随整技能目录分发

## 具体操作步骤

1. **盘点现有正文**：列出所有章节，按"入口判断 / 能力总览 / 方法 A / 方法 B / 字段表 / 模板"归类
2. **确定主体保留**：frontmatter + 什么时候用 + 入口判断 + 路由表，其余全部候选移出
3. **划分子文档**：每个独立方法一个文件，命名 kebab-case 放 `methods/`，子文档内部自己也有"为什么/怎么做/完成标准"三件套
4. **重写主体路由**：主体表格里列"需求 → 读哪个文件"；正文用 `Read`、`Glob` 指引（工具名写进正文时用反引号包裹，避免 lint 裸命令警告）
5. **更新 description**：把"主体 + 子文档按需读取"这个能力面写进描述（如"按主体入口判断 + 子方法按需读取执行"），让 AI 知道该技能是分层结构
6. **自检与测试**：重走 `generate.md` 第五步自检（尤其威胁扫描要覆盖 methods/ 等附属文本）、第六步测试

## 拆分示例（本技能 v2.0.0 即此结构）

```
skill-creator/
├── SKILL.md              # 主体：披露 + 何时生成/调用 + 摆放 + 路由表（~90 行）
└── methods/
    ├── generate.md       # 生成与修改技能：六步全流程 + 字段表 + lint 速查
    ├── merge.md          # 融合与淘汰：查重 → 融合 → 丢弃
    └── split.md          # 本文件：拆分方法论
```

## 拆分完成标准

- [ ] 主体 ≤200 行，只剩披露、入口判断、路由
- [ ] 每个独立方法一个子文档，命名 kebab-case，放技能目录下
- [ ] 主体路由表覆盖所有子文档路径，AI 能按需 `Read` 定位
- [ ] description 已声明分层结构；自检四轮全部通过（含 methods/ 威胁扫描）
- [ ] 测试：触发命中主体、执行时能正确路由到子文档
