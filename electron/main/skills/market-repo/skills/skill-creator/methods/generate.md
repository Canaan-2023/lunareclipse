# 生成与修改技能的方法（Generate & Modify）

本文件是 skill-creator 的「怎么生成」子文档：从捕获意图到测试验收的完整六步。需要改现有技能时同样适用（改哪个环节就重走该环节 + 自检）。

## 第一步 捕获意图

先回答四个问题，答案写在会话里，不写入文件，作为本轮设计判断的依据：

1. **这个技能做什么**——一句话说清能力边界（例："审查 PR 代码质量"）
2. **何时触发**——列出用户可能说出的原话（例："帮我看看这段代码"、"review 一下这个 PR"），这是 description 的素材
3. **输出什么**——交付物形态与结构（报告模板、文件、清单）
4. **验收标准**——什么情况下算做对（逐项核对清单）

## 第二步 设计 frontmatter

frontmatter 是 SKILL.md 开头的 `---` 代码块。只写有意义的值，不堆字段。

### 必填字段

| 字段 | 规则 | 示例 |
|------|------|------|
| `name` | kebab-case（小写字母/数字/连字符）、≤64 字符、禁 XML 标签、禁保留词（lunareclipse、moon） | `code-review` |
| `description` | 必填、≤1024 字符、禁 XML 标签；"做什么 + 何时触发"开头，核心触发词放在前 60 字符内 | 见下方写法 |

description 写法模板：

> 动词 + 对象 + 触发场景。触发：用户说 X、请求 Y、需要 Z 时使用。正文说明：……

正例（覆盖触发、边界、输出）：

> 用户请求代码审查、review PR、检查代码质量或分析 diff 时使用。按安全、性能、可维护性、正确性、测试维度审查 TypeScript/JavaScript/Python 代码。

反例（只描述自身，无触发信息）：

> 这是一个代码审查技能，包含详细的审查清单与输出格式。

### 常用可选字段

| 字段 | 作用 | 示例 |
|------|------|------|
| `version` | 版本号，`\w.+-` 允许 | `1.0.0` |
| `author` | 作者标识 | `ABYSSAC` |
| `license` | 许可证 | `MIT` |
| `domain` | 所属领域（kebab-case、≤32 字符） | `code` |
| `category` | 索引分组（无则归"通用"） | `meta`、`computer`、`testing` |
| `platforms` | 运行平台，仅允许 linux/macos/windows | `windows` |
| `user-invocable` | 是否允许用户直接调用 | `true` |
| `context` | 加载上下文：inline（正文注入当前会话）/ fork（子代理） | `fork` |
| `allowed-tools` | 子代理可用工具白名单 | `[bash, read]` |
| `paths` | 运行时相对路径映射 | `logs: logs/` |
| `dependencies` | 依赖的其他技能 | `[test-driven-development]` |
| `related-skills` | 关联技能（推荐给用户） | `[codebase-inspection]` |
| `requires-tools` | 必须存在的工具，缺失则提示 | `[use_skill]` |
| `fallback-for-tools` | 工具缺失时的降级描述 | `[browser_navigate: 改用搜索工具]` |
| `config` | 运行期可配置项 | `[max_depth: {type: number, default: 3}]` |
| `hooks` | 技能级生命周期钩子：`pre_execute`/`post_execute` 是技能执行前后的附加提示文本，**不是**宿主级每轮上下文注入（后者在正文用"宿主机制维度"描述，见第三步） | `[pre_execute: 输出降级方案]` |
| `tags` | 检索标签 | `[review, pr, diff]` |

## 第三步 撰写正文

正文 = 场景判断 + 步骤 + 输出模板 + 注意事项。推荐结构：

```markdown
# 技能名（可中英对照）

## 为什么存在        ← 一段话：解决什么问题，价值在哪
## 什么时候用        ← 触发清单（显式触发 + 边界：什么时候不用）
## 依赖宿主机制(run on host) ← 可选：技能依赖宿主的注入/状态/环境时写"有则转发、无则降级"
## 步骤/流程         ← 主线：编号步骤，每步写"做什么 + 判断依据"
## 输出模板          ← 固定结构，用代码块给出可直接套用的模板
## Gotchas           ← 常见陷阱（每行一条，简短）
## 完成标准          ← 可勾选清单，执行后逐项核对
```

写作规则：

- 步骤只写该技能的决策点：做什么、按什么判断、输出什么，不写通用编程知识
- 正文出现 shell 命令时用反引号包裹（如 `` `grep` ``、`` `cat` ``、`` `rm` ``），否则触发 lint 警告
- 不用夸大式营销词（如"无缝""革命级"这类无法验证的修饰语），改写为中性表述
- 禁用危险模式：不加动态代码执行、子进程调用、递归删除、函数构造器、原型链污染、环境变量读取等危险写法（具体命中规则由 lint 逐条扫描，命中即拦截）
- 行数目标：简单技能 40-100 行，复杂技能 150-400 行，不超 500 行

### 宿主机制维度（决定是否写"依赖宿主"一节）

先分清两类"钩子"，别混为一谈：

- **frontmatter `hooks`**：技能执行前/后附加的提示文本（`pre_execute`/`post_execute`），跟随技能生命周期，不是宿主注入。
- **宿主注入（host injection）**：宿主在每次 LLM 调用前把上下文值注入模型（如宿主的 `PreLLMCall` 钩子注入 `injectedContext`，模型收到的是一条"系统注入"的参考上下文）。技能正文可以**依赖并转发**这种注入值。

技能正文依赖宿主注入值时，按"有值则转发、无值则降级"两分支写死，禁止只写一半：

> 上下文出现宿主注入的 `Caveman mode: <mode>` 值：直接转发，不改写、不推断。无注入值（宿主未配置钩子）：报告本会话实际跟随的模式或 `off`，附 `(not tracked by this host)`。加载本技能回答状态查询不算激活。

判断要不要写：技能有"需宿主每轮注入的状态/模式/标记"→ 写；技能自包含、无状态 → 不写，不要无病呻吟。

### 正文自己太长了怎么办

一部正文超过 300 行、或同时承载"入口判断 + 多种方法"时，按 `split.md` 拆成主体 + 子文档：主体放什么时候用、能力总览与路由，详细方法放同目录子文档，正文用 `Read` 指引按需加载。不要为了"省事"把所有方法堆进一份正文。

## 第四步 保存技能

**两个文件夹、由 `source` 参数选层级**：用户级 = `skills/` 下扁平一个技能目录；领域级 = `skills_domains/{领域路径}/{name}/`，领域 = 目录层级（`code` 目录下是 `code` 领域、`writing` 目录下是 `writing` 领域，`design/web` 即多层级领域）。`skill_manage` 里 `source=user`（默认）写用户级、`source=domain` 时用 `domain` 参数指定领域路径写领域级。

运行期用 `skill_manage` 工具保存技能，动作说明：

| 动作 | 用法 | 注意 |
|------|------|------|
| `create` | 传入 name、body（正文全文）、description 及可选字段 | 新技能名不能与现有技能重复；需要用户授权；写入后自动校验，解析失败回滚 |
| `update` | 传入技能名 + 要修改的字段 | 修改已有技能的描述、正文、字段 |
| `delete` | 传入技能名 | 先向用户再次确认，再执行删除（删除技能目录与 SKILL.md 文件） |

`create`/`update` 传字段名时保持 frontmatter 字段一致（name/description/version/author/license/domain/category/context/allowed-tools/paths/platforms/dependencies/related-skills/tags/requires-tools/fallback-for-tools/config/hooks），正文整体传 `body`。

## 第五步 自检

按顺序跑四轮检查，任何一项不过都回到第二步/第三步修正：

1. **frontmatter 校验**：name 是 kebab-case 且 ≤64、无保留词/XML 标签；description 非空 ≤1024；platforms 只含 linux/macos/windows；domain 是 kebab-case ≤32
2. **lint 检查**：error 必须为零（name 非 kebab-case）；warning 不阻断加载，交付前清零（description >300 字符、正文裸命令），无法清零的说明原因
3. **威胁扫描**：全文（含 scripts/、methods/ 等附属文本）无危险模式——脚本注入、删除命令、管道执行、原型链污染等
4. **触发回读**：站在用户视角重读 description——"用户说出什么话会让 AI 检索到这份技能？"前 60 字符是否已经出现触发词

## 第六步 测试与迭代

用 2-3 个代表性提示词验证：

1. **触发测试**：写一个明确命中的提示词（例：技能是代码审查 →"review 一下这个 PR"），确认 description 能匹配
2. **边界测试**：写一个不该触发的提示词（例："帮我写段代码" 不应命中代码审查技能），确认不会误触发
3. **执行测试**：按正文步骤走一遍完整流程，核对输出与模板一致
4. **迭代**：执行中发现步骤缺失、判断标准含糊、输出模板不适用的，当场修改正文后再测；描述命中率低的，把用户原话补进 description

测试完成后向用户交付技能路径与三个测试结论（触发命中/边界不触发/执行符合模板）。

## 技能系统速查

### 加载机制（渐进披露）

| 阶段 | 模型看到什么 | 时机 |
|------|-------------|------|
| 技能清单 | name + description（只展示前 60 字符） | 常驻提示 |
| 领域摘要 | 领域名 + 技能数量 | 常驻提示 |
| 正文 | SKILL.md 全文 | 调用 `use_skill(skill_name=...)` 后加载 |
| 捆绑资源 | scripts/references/methods/assets | 正文指引需要时读取（`Read` 对应子文档/脚本） |

`use_skill` 不传参数 = 盘点全部技能；传 domain = 盘点该领域。context=inline 正文进入当前会话；context=fork 另起子代理（结合 allowed-tools 使用）。

### 宿主注入机制（技能转发依赖的载体）

宿主 Hook 引擎支持 `PreLLMCall` 事件：钩子以 `{ action: "continue", injectedContext: "..." }` 返回，注入值会被作为"系统注入"参考上下文插入每次 LLM 调用前。技能正文可声明转发该值；未配置钩子时无注入值，正文必须写降级行为（见"宿主机制维度"）。技能不控制宿主是否注入——它只描述"有则怎么用、无则怎么办"。

### lint 规则速查

- name 非 kebab-case → error
- description >300 字符 → warning
- 正文裸命令（shell 命令名未用反引号包裹，如 `grep`、`cat`、`rm`）→ warning
- 营销词（过度吹嘘的英文形容词，直接陈述能力即可）→ warning
- 危险模式（动态执行、任意命令拼接、递归删除、管道直通 shell、fork bomb、原型链污染、环境变量读取）→ 拦截

## 反模式

- **description 写"这是一个技能"**——浪费 60 字符窗口；直接写"做什么 + 何时触发"
- **正文写教程不写流程**——把"如何审代码"写成课堂讲义，而不是"按清单逐项核对"的可执行步骤
- **一个技能塞两个职能**——代码审查和编写文档是两回事；拆成两个技能
- **忽略误触发**——description 范围过宽导致无关请求命中；用边界词收窄
- **写完不测试**——没有触发测试与执行测试就交付，等于未验收
- **裸命令当正文**——写"用 `grep` 找"能把命令名包进反引号，举例时同样遵守，否则 lint 警告
- **主体塞满细节**——入口判断、能力总览、详细方法三层混在一份正文，体积失控；按 `split.md` 分层
- **转发只写一半**——只写"宿主注入值直接转发"，不写无注入值时的降级行为，宿主未配置钩子时技能行为悬空；按"有则转发、无则降级"两分支写全

## 生成完成标准

- [ ] frontmatter：name kebab-case 无保留词、description 非空且触发词前置、字段值合法
- [ ] 正文：有为什么存在/什么时候用/流程/输出模板/Gotchas/完成标准，≤500 行
- [ ] 保存技能：目录结构正确、与领域匹配、技能名不冲突；新领域已按目录层级成立
- [ ] 自检：校验 + lint + 威胁扫描全部通过（error 清零、warning 清零或已说明）
- [ ] 测试：触发命中、边界不触发、执行输出符合模板，三项均有结论
